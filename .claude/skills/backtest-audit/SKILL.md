# /backtest-audit — レジストリ外バックテストの監査（1起動＝1対象1監査）

「このバックテスト、信じていいか？」に規律で答える。監査対象の典型は
`agent_prompt_kaiten_backtest.md` 系の成果物・`output/` 配下の単発検証・持ち込みコード。

## ガードレール（違反不可）

1. **対象コードを書き換えない**（提案のみ。バグを見つけても修正パッチは提示に留める）。
2. **監査結果は「規律適合」の判定**であり、戦略の有効性認定ではない。有効性の認定は
   judge_grid＋事前登録＋DSR≥0.95 のみ（この位置づけを出力に定型で明記）。
3. 監査で有望に見えても research_loop/ には書かない。移植プランを人間に提示し、
   採用判断は BACKLOG 経由（/research-scout or 人間）。
4. 書き込みは `output/audit/` のみ。

## 手順

### Step 1 対象の把握
スクリプトと入出力（データ源・期間・ユニバース・パラメータ・結果ファイル）を読み、
「何を・どの期間で・どう検証したか」を5行で要約（誤読があると監査全体が無効になるため、
不明点はここで列挙して UNKNOWN 扱いを宣言）。

### Step 2 チェックリスト（各項目 PASS/FAIL/UNKNOWN＋証拠行）
PLAYBOOK §A-6/§A-8 と LESSONS 失敗型タクソノミーを判定基準にする:
1. **先読み**: シグナルは ≤t 情報のみか。執行は判定足の終値で建てていないか
   （execution_lag=1 / T+1 始値相当か）。
2. **生存者バイアス**: ユニバースは PIT か（現在の構成銘柄で過去を回していないか）。
   上場廃止リターンを含むか。
3. **財務 as-of**: fundamentals は DiscDate ラグ付きか（決算値を発表前に使っていないか）。
4. **in-sample パラメタ**: 閾値・銘柄リスト・ブラックリストが検証期間と同じデータから
   作られていないか（kaiten の既知欠陥型）。探索した組合せ数 = 実効 K はいくつか。
5. **コスト現実性**: 片道コストが床（月次XS 15bps／日次イベント 30bps／貸株 115bps+・
   小型 300bps）以上か。ストップ高安の値幅ロック（UL/LL）を約定可能性に反映しているか。
6. **容量**: ADV×participation 10% で運用可能額はいくらか（¥数千万未満は実運用不可級）。
7. **多重検定**: 試行が記録されているか。報告 Sharpe を K で DSR 換算すると残るか
   （`invest_system/validation/dsr.py` で概算してよい＝読み取り計算のみ）。
8. **OOS 汚染**: 2024-01 以降のホールドアウトを設計・選択に使っていないか。
   サブ期間（特に 2023-26）で符号が保つか。

### Step 3 判定と移植プラン
- **総合判定**: 監査 PASS（規律適合・結果は额面どおり読める）/ 条件付き（FAIL 項目の
  影響を定量で見積もれる）/ 監査 FAIL（結果は設計根拠に使用不可）。
- **移植プラン**（判定に関わらず提示）: Strategy IF 化の骨子（既存テンプレ:
  `research/strategy.py`・雛形 examples は PLAYBOOK Step 4 参照）、judge_grid の scope 案・
  グリッド（≤6セル）・コスト/frictions 配線、想定 K。事前登録ドラフト本体は書かない
  （それは /research-cycle Step 3 の仕事）。

### Step 4 出力
`output/audit/{対象名}_{YYYYMMDD}.md`: 要約 / チェックリスト表（証拠行番号付き）/
総合判定 / 移植プラン / 定型注記（ガードレール2）。ユーザーには FAIL/UNKNOWN 項目と
総合判定を1画面で。

## 運用メモ
- kaiten 系の初回監査が最初の実戦（メモリの既知欠陥: パラメータ/ブラックリストが
  in-sample・registry/DSR 規律の外）。
- 外部エージェントに検証を依頼する前にこのチェックリストを依頼プロンプトへ埋め込むと、
  監査 FAIL の手戻りが減る（coding_agent_prompt v2.1 §1-§7 と同型）。
