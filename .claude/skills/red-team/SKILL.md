# /red-team — 事前登録の敵対的レビュー（1起動＝1対象）

安価な「判定の内ループ」＝実データに触れる前に設計を攻撃して K を節約する。
対象: docs/NN の §0-§3 草稿・BACKLOG の ⬜ 項目・ユーザー持ち込みのアイデア。

## ガードレール（違反不可）

1. **K=0・読み取り専用**: バックテスト・ローカルリターン参照・registry 書き込み禁止。
   レビュー対象ファイルも**書き換えない**（修正は引用付きの提案として出す）。
2. **役割は「落とすこと」**: 弁護しない。生き残った設計だけが価値を持つ。
   ただし攻撃は具体的でなければならない（「リスクがある」は禁止・「H-16 により
   12ヶ月窓のΔシグナルは同窓 momentum と機械的に相関するが、コントロールに
   momentum(12-1) が無い」のように条文と欠落を特定する）。
3. 書き込み先: `research_ops/redteam/` のみ。コミットは1回。

## 手順

### Step 1 文脈ロード
レビュー対象＋`research_loop/HEURISTICS.md`（全 H-n）・`LESSONS.md`（F1〜n＋サイクル記録）・
`BACKLOG.md` §2 除外リスト・PLAYBOOK §A（ガードレール）・（対象が引用する）出典。

### Step 2 機械照合（全項目・表形式で判定）
1. **H-n 全数照合**: H-1〜最新まで1件ずつ「該当/非該当/違反疑い」を判定（スキップ禁止）。
2. **F-n 予想**: この設計はどの失敗型で死ぬ確率が最も高いか上位2つ＋確率感。
   §0 の回避表に**漏れている型**がないか。
3. **PIT リーク狩り**: シグナル構築の記述を1行ずつ読み「その値はその時点で本当に
   既知か」を問う（開示ラグ・公表時刻・遡及改訂・ユニバース選択の先読み・
   執行タイミング）。過去の実例（margin_weekly の公表ラグ・submit_dt の時刻）と突合。
4. **K 会計監査**: グリッド≤6/予算≤8 か・scan の計上漏れ・セルの実質重複
   （同一仮説の分位違いを別仮説と数えていないか）・**統制セルの有無（H-18）**。
5. **合格基準の well-formedness**: 副次基準が「緩和」方向に働く余地がないか・
   事後救済の抜け道（§3 ステージの書き方が曖昧で後出しを許さないか）。
6. **AHM 7カテゴリ**（動機/多重検定/データ/CV/モデル動学/複雑度/文化）を1行ずつ。
7. **より安価なキルチェック**: 実行前に K=0 で判定を殺せる記述スキャン・概算
   （H-12 型の SR 上限計算等）を具体的に提案。

### Step 3 判定とレポート
- 判定: **approve**（そのまま実行可）/ **revise**（具体的修正案リスト付き・修正後は
  再レビュー不要の軽微〜要再レビューの重大を区別）/ **reject**（BACKLOG へ差し戻し・
  棄却理由は Stage-0 棄却台帳への記載文まで書く）。
- `research_ops/redteam/YYYY-MM-DD-<scope>.md` に全照合表＋判定を記録。
- `git add research_ops/` → `ops(red-team): <scope> — <判定>`。
- サマリ: 判定・最重要指摘 3件以内・修正案。

## 運用メモ
- research-cycle の Step 3（事前登録）とコミット①の**間**に挟むのが定位置
  （PLAYBOOK §B に任意ステップとして記載）。人間の持ち込みアイデアの一次スクリーンにも使える。
- レビューが甘かった場合（実行後に red-team が見逃した型で FAIL）、その見逃しを
  LESSONS のサイクル記録に含める＝レビュー自体も学習対象。
