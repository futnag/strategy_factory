# 07 — ファンド手法サーベイの統合と新規戦略候補（2026-06）

日本株を運用するファンド（アクティビスト／L/S／クオンツ／イベントドリブン）の手法を
2系統の調査（Claude web サーベイ＋別 AI エージェントのレポート）で収集し、
**本ファクトリの裁定台帳（docs/03）と突合**した結果の整理。目的は、
(a) 裁定済み scope の再試行という K 規律違反を犯さないこと、
(b) 未裁定かつ PIT 実装可能な候補だけを事前登録の形に落とすこと。

> 結論の先取り：サーベイ提案の大半は「実装済み」か「裁定済み FAIL」だった。
> 本当に新しいのは **開示文書データ層（EDINET / 適時開示）の追加**であり、
> これ1つで未裁定のイベント族3つ（TOB アーブ・大量保有イベント・自社株買い発表）が
> 解錠される。§6.17 に記録済みのデータ限界（「タイムリーな買い戻し発表イベントは
> 適時開示データが必要」）への直接の回答でもある。

**突合の含意**：2系統のサーベイで「個人に応用可能」とされた手法のうち、

これは偶然ではなく、J-Quants（価格・財務サマリー・信用・指数・フロー）の範囲は
すでに 26 scope・711 試行で掘り尽くされている（§6.19 総括）ことの裏返し。

## 2. 新規データ層 — 開示文書パイプライン（前提工事）

候補 C1〜C4 はすべて同じデータ層に依存する。戦略より先にここを作る。

### 2.1 `data/sources/edinet.py`（EDINET API・無料・要 API キー）
- 金融庁 EDINET API v2。日付別の書類一覧 → docTypeCode でフィルタ →
  必要書類のメタデータ（提出日時・提出者・対象会社 EDINET コード）を by-date ミラー
  （J-Quants ミラーと同じ流儀。**提出日時がそのまま PIT アンカー**になるのが最大の利点）。
- 対象書類：大量保有報告書／変更報告書（C2）、公開買付届出書・意見表明報告書・
  撤回届出書（C1）、有価証券報告書 XBRL（C4 の BS 明細）。
  ※ docTypeCode の具体値と書類保存期間（種類により異なる）は API 仕様書で要確認。
  ここに誤った定数を書くより、実装時に仕様書から落とすこと。
- 市場データではなく法定開示＝**ミラーのコミット可否は EDINET 利用規約を確認**
  （リファレンス化できれば index_events.py と同じ「コミット可能資産」になる）。

### 2.2 アクティビスト名簿 registry（コミット可能・公開リファレンス）
- index_events.py と同じ curate 方式。大量保有報告書の**提出者名は表記揺れが多い**
  （ファンド本体／GP／共同保有者名義）ため、名寄せ表が戦略の質を決める。
- 初期名簿（2系統サーベイから）：エフィッシモ、シティインデックスイレブンス・レノ・
  南青山不動産（村上系）、ストラテジックキャピタル、3D インベストメント、オアシス、
  エリオット、バリューアクト、ダルトン／ライジング・サン／NAVF、AVI、LIM アドバイザーズ、
  パリサー、シルチェスター、みさき投資、マネックス AF、ひびき、カナメ、Sengu、
  MY.Alpha 等。各行に：正式名・別名リスト・拠点・スタイル（強硬/友好）・出典 URL。
- 出典例：activist-media.net の保有一覧、大和総研「アクティビスト投資家動向」
  （2024 年総括）、各社大量保有報告書原本。**名簿に載せる基準も事前に固定**
  （後から「効く投資家だけ残す」名簿いじりは in-sample 選択そのもの）。

### 2.3 適時開示（TDnet）の現実
- 自社株買い取得枠・TOB 開始公告の最速ソースは TDnet だが、**公式 API がなく
  公開閲覧は直近 1 ヶ月のみ**。過去データのバックフィルが最大の課題
  （商用アーカイブ or 今日から自前で蓄積開始＝フォワード専用データ）。
- 現実解：C1 は EDINET の公開買付届出書（法定・遡及取得可）を一次ソースにし、
  TDnet は将来のリアルタイム化で使う。C3 は「今から蓄積→フォワード検証」が誠実。

## 3. 新規戦略候補（優先順・事前登録ドラフト）

### C1: TOB 成立スプレッド捕捉（リスクアーブ）— 最優先
- **仮説**：TOB 発表後の市場価格と買付価格のスプレッドは「不成立・撤回・延長リスク」への
  プレミアム。**アノマリーではなくリスクプレミアム**なので、§6.14・§6.17 を殺した
  「有名になった歪みは混雑で死ぬ」系譜に属さない（保有者がリスクを引き受ける対価は
  混雑で圧縮されても符号は残るのが通常）。これが prior を中立以上に置く根拠。
- **経済的根拠**：TOB 件数は 2024 年に過去 10 年最高水準、MBO・非公開化・PE 案件が
  構造的に増加中＝イベント数 N が検定に足る規模になりつつある稀な領域。
  かつ 1 件あたり容量が小さく機関が取り切れない＝個人向きの隙間（§6.14 と同じ論法）。
- **PIT**：公開買付届出書の EDINET 提出日時。エントリーは T+1 始値（DP17 そのまま）。
- **frictions**：値幅制限張り付き（DP15 の既存実装が**そのまま**効く領域）、
  発表直後の薄い板、不成立時のテール（発表前水準への急落）。
- **設計案（scope `tob_arb`・K=4・ロングのみ）**：
  spread 下限 {1%, 3%} × 保有 {成立予定日まで, 上限 40 営業日} の 2×2。
  対象は現金 TOB のみ（株式交換は除外）、案件分散の等加重。
  成立/不成立/条件変更の結果テーブルを index_events.py 方式で curate
  （撤回届出書・訂正届出書から機械的に判定できるか先に確認）。
- **先行確認事項**：不成立率と不成立時ドローダウンの分布。これが厚いと
  「拾うのはプレミアムでなく爆弾」になる。診断を先に、賭けは後に。

### C2: アクティビスト大量保有イベント（5% 超開示ドリフト）
- **仮説**：名簿掲載ファンドの新規 5% 超開示後、(i) 情報の漸進的織り込みと
  (ii) 同ファンドの継続買い増し需給でドリフトが出る。
- **対抗仮説（§6.17 の教訓）**：注目度が高すぎて発表時に即時（過剰）織り込み→フェード。
  配当改訂がまさにこの形で死んだ。**どちらに転ぶかは prior では決められない**ので、
  事前登録は drift_lt を主系とし、フェードへの後知恵スイッチは §6.14 規律ノートと
  同じく封印する。
- **PIT**：EDINET 提出日時（報告義務発生から 5 営業日以内の提出ラグは制度上不可避＝
  「ファンドの買値」より必ず遅れて知ることを織り込んだ検証になる。むしろ現実的）。
- **設計案（scope `activist_5pct`・K=4）**：保有 {20, 60 営業日} × 名簿 {強硬系のみ, 全量}。
  小型株に集中するため容量・値幅制限・貸借区分（DP15）の現実モデル必須。
- **副産物**：名簿×保有銘柄パネルは、C4（アクティビスト好み属性の先回りスクリーン）の
  教師データにもなる。

### C3: 自社株買い「発表」イベント — §6.17 データ限界の解消
- §6.17 の死因は「四半期スナップショット（ΔTrShFY）は適時開示より数ヶ月遅い陳腐化情報」
  だった。**取得枠設定の発表日**ベースなら別仮説＝新 scope が正当化される。
- ただし同節のもう一つの発見（PBR 改革後、還元ニュースは即時織り込み→フェード）は
  発表ベースにも当てはまり得る。**prior は中立以下**。順位を C1・C2 の後に置く理由。
- データは §2.3 の制約により「今から蓄積→フォワード」が現実解。Phase 2 の夜間ジョブに
  TDnet 収集を足しておき、1〜2 年分溜まってから裁定するのが K 効率がよい。

### C4: ネットキャッシュ調整バリュー（清原変種）— 旗艦の改良候補
- **内容**：タワー K1（25 年で 93 倍）の中核指標
  「ネットキャッシュ比率 ＝（流動資産＋投資有価証券×0.7 − 負債総額）÷ 時価総額」と
  「（時価総額 − ネットキャッシュ）÷ 時価総額 × PER」（実質 PER）。
  旗艦の value（book-to-market）と同族だが、**現金性資産の質で割安を測り直す**点が異なる。
  小型株に張る根拠（機関が入れない領域での個人優位）も旗艦の容量哲学と整合。
- **データ障壁**：fins/summary の項目は Sales/OP/OdP/NP/EPS/BPS/Eq/EqAR/TA のみ＝
  流動資産・投資有価証券・負債総額が**無い**。EDINET XBRL（有報）からの抽出が必要で、
  パイプライン工数は C1・C2 より重い。
- **規律上の警告**：これは「新戦略」ではなく**旗艦 value の精緻化**に近い。
  §8 は「研究はこれ以上の在サンプル精緻化が過学習と隣接する地点にある」と明記しており、
  旗艦 scope 内で B/M をネットキャッシュ版に差し替えて回すのは禁じ手。
  やるなら (a) 独立 scope として K を払い一発判定、または
  (b) Phase 2 に小口の並走スリーブとして置きフォワードのみで観察、のどちらか。
  **推奨は (b)**。清原指標の真価は 3〜5 年保有の複利にあり、月次 DSR 判定と相性が悪い。

## 4. 低優先・不採用（理由つき）

| 候補 | 理由 |
|---|---|
| バンプトラージ | 事例 ~8 件/数年＝統計検定不能。C1 の診断テーブルに「MBO×名簿ファンド介入あり」フラグだけ立てておき、定性ウォッチに留める |
| TOPIX 2026 定期入替 | 新制度で混雑の歴史こそ無いが、N225 の死（§6.14）と同じ捕食者が初日から待ち構える市場環境。イベント表の curate コストに対し prior が低すぎる。index_events.py の拡張余地としてメモのみ |
| SuMi 型 earnings-surprise MN ペア | 旗艦 short 側の OOS 失敗（§7.2）と同じ死因を別包装で踏む |
| OQ 型 quantamental | 人間オーバーレイはファクトリの判定対象外。Nick Bird の経歴（Macquarie 時代に AUM 過拡大とバリュー不調で閉鎖→OQ で容量キャップ運用）は**容量規律の教材**として §8 系の教訓に合致 |
| HFT・板情報系 | 日足ファクトリの解像度外。§6.14 診断（歪みが発表直後の数分〜数日に圧縮）が示す通り、ここを獲るにはインフラごと別物 |

## 5. 実装順序の提案

1. `data/sources/edinet.py`（書類一覧ミラー＋メタデータ）— C1/C2/C4 の共通前提
2. TOB 結果テーブル curate（届出・訂正・撤回から成立/不成立を機械判定できるか PoC）
3. **C1 を scope `tob_arb` で事前登録・裁定**（K=4）
4. アクティビスト名簿 registry → **C2 を scope `activist_5pct` で裁定**（K=4）
5. Phase 2 夜間ジョブに TDnet 蓄積を追加（C3 のフォワード準備・判定は寝かせる）
6. C4 は EDINET XBRL 抽出の工数を見て、Phase 2 並走スリーブ（フォワード観察）として設計

サーベイ 2 系統の正味の寄与：**「何を試すか」より「何を試さなくてよいか」**。
別 AI レポートのクオンツ提案は本ファクトリが既に走破した道であり、
Claude 調査のイベント系提案の半分は裁定済み FAIL だった。残った C1〜C4 は、
いずれも「ファクトリがまだ持っていないデータ」の先に居る。装置は完成している。
次に増やすべきは仮説ではなくデータ層、という結論。
