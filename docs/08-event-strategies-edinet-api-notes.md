## 1. API 構成（2 本のみ）

### 1.1 書類一覧 API
```
GET https://api.edinet-fsa.go.jp/api/v2/documents.json
    ?date=YYYY-MM-DD &type={1|2} &Subscription-Key={KEY}
```
- type=1: メタデータのみ（件数・更新日時）。type=2: 提出書類一覧＋メタデータ。
- date は当日以前・**直近の財務局営業日の 24 時において 10 年を経過していない日付**
  （土日祝も指定可。書類が無い日は count=0）。
- レスポンスは UTF-8 JSON。日時は日本時間。

### 1.2 書類取得 API
```
GET https://api.edinet-fsa.go.jp/api/v2/documents/{docID}
    ?type={1..5} &Subscription-Key={KEY}
```
| type | 内容 | 形式 |
|---|---|---|
| 1 | 提出本文書＋監査報告書（XBRL 含む） | ZIP |
| 2 | PDF | PDF |
| 3 | 代替書面・添付文書 | ZIP |
| 4 | 英文ファイル | ZIP |
| 5 | **XBRL→CSV 変換済みデータ**（csvFlag=1 のみ） | ZIP |

- 成功/失敗は HTTP ステータスでなく **Content-Type で判定**
  （octet-stream/pdf=成功、application/json=エラー）。エラー JSON でも HTTP 200。
- ステータス: 400/401/404/429/500。429 が定義済み＝礼儀的スロットリング必須
  （J_QUANTS_MIN_INTERVAL と同じ env 方式 `EDINET_MIN_INTERVAL` を推奨）。

### 1.3 認証
- 閲覧サイトでアカウント作成（メール＋SMS/音声 MFA）→ API キー発行。
- **2 年以上未使用の API キーは自動削除**（Phase 2 夜間ジョブで毎日叩くなら問題なし）。

## 2. 一覧レスポンスの重要フィールド（戦略への対応）

| フィールド | 内容 | 使う候補 |
|---|---|---|
| `docID` | 書類管理番号（一意） | 全部（取得 API のキー） |
| `submitDateTime` | 提出日時 YYYY-MM-DD hh:mm | **全候補の PIT アンカー** |
| `secCode` | 提出者の証券コード（5 桁） | J-Quants LocalCode と突合 |
| `edinetCode` / `filerName` | 提出者 | C2 名簿マッチ（filerName は表記揺れ前提） |
| `ordinanceCode` | 府令コード | 後述のフィルタ |
| `formCode` | 様式コード（別紙1） | C2 一般様式/特例様式の識別 |
| `docTypeCode` | 書類種別コード | 後述のフィルタ |
| `issuerEdinetCode` | **大量保有の発行会社**（=対象銘柄） | **C2**（本文パース不要で対象特定） |
| `subjectEdinetCode` | **公開買付けの対象会社** | **C1**（同上） |
| `parentDocID` | 親書類の docID | **C1 の案件チェーン構築** |
| `withdrawalStatus` | 取下書=1 / 取下げられた書類=2 | ミラー整合 |
| `docInfoEditStatus` / `disclosureStatus` | 職員修正・不開示区分 | ミラー整合 |
| `xbrlFlag` / `csvFlag` / `pdfFlag` | 形式有無 | 取得 type の選択 |
| `legalStatus` | 1=縦覧中 / 2=延長期間中 / 0=閲覧期間満了 | §4 の制約管理 |

### 2.1 フィルタ定数（仕様書本文で確定）
府令コード（ordinanceCode）:
- `040` 発行者以外の者による株券等の公開買付け（第三者 TOB）→ **C1 対象**
- `050` 発行者による上場株券等の公開買付け（自社株 TOB）→ C1 から除外
- `060` 株券等の大量保有の状況の開示 → **C2 対象**

書類種別コード（docTypeCode）:
- `240` 公開買付届出書（**C1 イベント起点**）
- `250` 訂正公開買付届出書（**価格変更＝バンプ検出**）
- `260` 公開買付撤回届出書（不成立系）
- `270` 公開買付報告書（**結果報告＝成立/応募数の一次ソース**）
- `290`/`300` 意見表明報告書（賛同/反対＝成立確率の特徴量候補）
- `310` 対質問回答報告書
- `350` 大量保有報告書（**C2 イベント起点**）・`360` 訂正大量保有報告書
- `120`/`130` 有価証券報告書・訂正（**C4 の BS 明細ソース**）
- ※ 変更報告書（保有割合の増減）の正確なコードは**別紙1で要確認**。
  府令 060 で一覧を引けば取りこぼしは無い。

### 2.2 C1 案件チェーンの構築規則
仕様書 4-1: 公開買付報告書・撤回届出書・対質問回答報告書・意見表明報告書の
parentDocID には**報告対象の公開買付届出書の docID** が設定される。
訂正報告書の parentDocID は訂正前書類（提出操作上設定されている場合のみ＝欠損あり得る）。
→ deal_id = 起点 240 の docID。240 を起点に parentDocID で 250/260/270/290 を集約し、
  `equities/tob_events.py` の案件テーブル（announce, target, price, 結果, バンプ有無）を生成。

## 3. ミラー設計（`data/sources/edinet.py`）

J-Quants と同じ **by-date ミラー**。ただし EDINET 固有の挙動に対応：

1. **増分取得**：seqNumber は同一ファイル日付内で不変・追記専用。
   当日分は「前回取得の最終 seqNumber より大きいもの」で漏れなく増分化できる。
2. **当日分**は 8:30 過ぎから原則 1 分毎更新。**過去分**は 24 時過ぎの日次更新処理で
   全ファイル日付が差し替え。**当日分ファイルが出現＝前日分確定**のシグナル
   （Phase 2 夜間ジョブ 21:30 JST 時点では「前日分まで確定・当日分は進行中」）。
3. **追記専用スナップショット推奨**：取下げ（null 化）・職員修正・不開示・
   閲覧期間満了（null 化）が**過去日付のレコードを書き換える**ため、
   「初回観測時スナップショット」を保全すると PIT 監査が可能になる
   （日次更新で消える前の情報を保持できるのはローカルミラーだけ）。
4. **名寄せ**：EDINET コード集約一覧 CSV（廃止コード→継続コード）と
   EDINET コードリスト（最新属性）で edinetCode を正規化。
   filerName 直接マッチは最後の手段（C2 名簿は edinetCode ベースで持つ）。
5. **レート制限**：数値仕様は非公開（429 のみ定義）。min-interval スロットル＋
   指数バックオフ。一覧は 1 日 1 リクエストで済むため負荷は軽い。
   重いのは書類本体（C4 の有報バックフィル）のみ。

## 4. 閲覧期間の制約（バックテスト深度に直結・最重要）

- API の取得対象は**縦覧期間＋延長期間（=閲覧期間）内の書類のみ**。
- 延長期間が設けられるのは：有価証券報告書 5+5=**10 年**、半期報告書 5+5=10 年
  （2024-04 以降提出分）、四半期報告書 3+7=10 年（2015-04 以降提出分）。
- **大量保有報告書・公開買付関連は延長表に含まれない**＝法定縦覧期間のみ
  （一般に 5 年とされる。正確な年数は金商法の条文で要確認）。
- 閲覧期間満了で、**一覧レコード自体が docID 以外 null 化**され、本体も取得不能。

**含意**：
- C1/C2 のバックテスト深度は**最大 ~5 年**を想定して検出力を設計
  （TOB は 2024 年が過去 10 年最多なので直近 5 年でも N は相応に確保できる見込み）。
- C4（有報）は 10 年遡及可能。ただし 2013-01-04 以降提出分（仕様書 3-1-9-2）。
- **ミラーを今日から回すこと自体が、公式ソースから消えていくデータを固定化する
  資産形成**になる。index_events.py の curate と同じ思想で、取得済み一覧の
  ローカル永続化を最優先。

## 5. TDnet との棲み分け（docs/07 §2.3 の精緻化）

| 開示の種類 | 媒体 | 候補 |
|---|---|---|
| 法定開示（有報・大量保有・公開買付届出書・臨報） | **EDINET**（当日 1 分毎反映） | C1 / C2 / C4 |
| 適時開示（決算短信・自社株買い取得枠・業績修正） | TDnet（公式 API なし・公開は直近 1 ヶ月） | C3 のみ |

- C1/C2/C4 は **EDINET 完結**。リアルタイム性も足りる。
- TOB の最速一報は適時開示（「開始のお知らせ」）が届出書より先行し得るが、
  PIT アンカーに届出書 submitDateTime を使うのは**保守的（遅い側）**で問題なし。

## 6. 形式の選択（XBRL vs CSV vs PDF）

- type=5 の CSV（XBRL の機械変換）が使えれば、C2 の保有割合・保有目的、
  C4 の BS 項目（流動資産・投資有価証券・負債合計）の抽出は**タクソノミ処理なし**で可能。
- CSV は 2023-01 システム更改で導入されたため、**それ以前の提出分は csvFlag=0 の
  可能性が高い**（要実測）。C4 の 10 年バックフィルは旧分=XBRL・新分=CSV の
  二系統パーサになる前提で工数を見積もる。
- 一部の確認書等は PDF のみ（ユーザー確認済み）。C1〜C4 の対象書類は
  xbrlFlag/csvFlag で機械判定してから取得する。

## 7. PoC 初日に実測で潰す確認事項

1. **別紙1 様式コードリスト**：府令 060 配下の様式（一般様式/特例様式/変更報告書）の
   formCode。特例様式（機関投資家の集約報告）は報告ラグが長く、C2 の PIT 設計に直結。
2. **csvFlag の実態**：2023-01 前後の書類でサンプリングし、CSV 提供範囲を確定。
3. **大量保有・TOB 書類の正確な縦覧期間**：直近 5〜6 年の日付で一覧を引き、
   legalStatus=0（null 化）が始まる境界日付を実測。
4. **変更報告書の docTypeCode**：350/360 以外に割当てがあるか、府令 060 の全件で確認。
5. 大量保有 CSV/XBRL の中身：保有割合・共同保有者・保有目的のタグ位置。

PoC スクリプト案：`examples/edinet_probe.py`
（任意の 1 週間分の一覧を取得 → 府令 040/050/060 の件数・フィールド充足率・
csvFlag 分布・特例様式比率をレポート。jquants_markets_probe.py と同型）

### 7.1 実測結果（2026-06-13・`examples/edinet_probe.py` ライブ実行）

直近 7 営業日（2412 件）＋過去 1〜7 年前の各 1 日を実取得して 5 点を確定した。

- **point3 縦覧期間境界＝最重要・C1/C2 の検証深度を直接規定**：フィールド充足率は
  1 年前 97.5% → 2 年 76% → 3 年 76% → **4 年（2022-06）50.8% → 5 年（2021-06）17%**
  と崩落。legalStatus=0（閲覧期間満了で docID 以外 null 化）が 5 年で多数派。残存
  16〜22% は legalStatus=2（延長期間中）の有報等（10 年保存）。
  → **TOB/大量保有の EDINET 実効窓は今日実行で実質 ~4 年（2022 半ば〜）**。docs/09
  §2.2 の「2021〜が一次ソース窓」は、2021 年分が既に ~83% null 化済みのため**今日時点
  では 2022+ に後退**。これは「今からミラーを回すこと自体が資産形成」（§4）の数値的
  裏づけ＝2022 年分も ~1 年で公式から消える。**初回ミラーと夜間追記を最優先**。
- **point2 csvFlag**：直近窓は大量保有 967/967・TOB 4/4・有報 263/267 が csvFlag=1
  ＝CSV（XBRL 機械変換）で抽出可。§6 の「2023-01 前は csvFlag=0 の可能性」は、上記の
  通り旧分が縦覧満了で消えるため C1/C2 では実害が小さい（C4 有報のみ 10 年で旧 XBRL
  二系統が残る）。
- **point4 変更報告書の docTypeCode**：府令060 は **docTypeCode 350(661)/360(306) の
  2 種のみ**。350 が新規・変更の両方を含み 360 が訂正＝**docTypeCode では新規/変更を
  峻別できない**。
- **point1 新規/変更/訂正の峻別＝本体タイトルが唯一の真値（2026-06 本体実測で訂正）**：
  当初は formCode 接頭辞で機械分類できると記したが、本体（type=5 CSV）の
  `jplvh_cor:DocumentTitleCoverPage` を実測した結果 **formCode は新規/変更を判別できない**
  ことが判明した。反例：`010000` に「変更報告書No.12」が混入（4/40）、`010002` は 40/40 が
  「変更報告書」（旧記載の "010002=新規" は誤り）。正しい判定は本体タイトル：
  「訂正」を含む→訂正／「変更報告書」を含む→変更／「大量保有報告書」のみ→新規。
  実装は `large_holdings.report_class()`。
  - formCode で**信頼できるのは一般/特例の別だけ**（接頭辞 01=一般、02/03=特例）。特例報告
    （法27条の26・基準日方式）は**重要提案行為等の意図がない機関投資家専用**で、実測でも
    特例新規 `030000` の重要提案ヒットは 0/25。→ **C2 アクティビスト母集団のスキャンは
    一般新規 `010000`（≈4,884 件）に限定でき**、新規イベントは事実上すべてここに入る
    （`010002` は 100% 変更）。`large_holdings.is_special_report()`。
  - `090001`＝訂正報告書（=docType 360）。
- **point5 大量保有 CSV のタグ（要素 ID 実測確定 2026-06）**：type=5 は UTF-16 TSV、
  名前空間 `jplvh_cor`/`jpdei_cor`。C2 で使う要素 ID（`large_holdings.py` に定数化）：
  保有目的=`jplvh_cor:PurposeOfHolding`（重要提案行為等の判定対象）、株券等保有割合=
  `HoldingRatioOfShareCertificatesEtc`（0.0902=9.02%）、直前報告割合=
  `…EtcPerLastReport`、提出者＋共同保有者総数=`TotalNumberOfFilersAndJointHoldersCoverPage`、
  本体タイトル=`DocumentTitleCoverPage`（新規/変更/訂正の真値）、提出者 EDINET コード=
  `jpdei_cor:EDINETCodeDEI`、報告義務発生日=`DateWhenFilingRequirementAroseCoverPage`
  （**PIT 非使用**・提出ラグ特徴量用）。タクソノミ処理不要で抽出可。
- フィールド充足率（直近窓）：submitDateTime **100%**（PIT アンカーは常時取得可）、
  filerName 99.8%、issuerEdinetCode 40.1%（=大量保有比率）、parentDocID 33.7%、
  secCode 33.5%（ファンドは secCode 無し）、subjectEdinetCode 0.3%（TOB のみ）。

## 8. 外部データソース：M&A Online データベース（§4 の閲覧期間制約への対策）

出典：https://maonline.jp/pages/taihouser （運営：ストライク・グループ）

### 8.1 大量保有報告書データベース（C2 の歴史バックフィル候補）
- 収録：**2007-04-01 以降に提出された大量保有報告書の全データ**（約 19 年分）
  ＝ EDINET API の閲覧期間制約（~5 年で null 化）を埋める唯一級のソース。
- フィールド：報告義務発生日／対象会社／保有者／種別（新規=大量保有報告書・
  変更=変更報告書）／増減（当該報告の保有割合 − 直前報告の保有割合）。
  提出日ベースで集計＝**提出日（PIT アンカー）と報告義務発生日の両方を保持**。
- 粒度：提出日は日単位とみられる（分単位は EDINET API のみ）。月次〜日次の
  検証ファクトリには十分。
- 品質：運営元が「提出者の記入間違い・データ破損により実態と相違があり得る。
  正式は EDINET で確認」と明記 → **直近 ~5 年の重複期間で EDINET API ミラーと
  突合検証**（§6.21 上流汚染監査と同じ mask-first 流儀）を必須工程とする。
- 利用条件：**利用規約（maonline.jp/pages/policy）を実装前に確認**。
  手動ブラウザダウンロード（一回限りの歴史バックフィル）を想定し、
  スクレイピングの可否・二次利用条件は規約準拠。取得データは J-Quants 同様
  `data/`（gitignore）にのみ保持、コミットしない。

### 8.2 TOB データベース（C1 のバックフィル・**調査済み確定版**）
- URL：一覧 `maonline.jp/db/tob/{年}`、詳細 `maonline.jp/db/tob/{年}/{連番}`。
  収録は **2008 年〜（約 18 年分）**。一覧＝公表日・対象会社（証券コード）・買付者・
  進捗（成立/不成立）・プレミアム・終了日＋敵対的/MBO フラグ。年別集計バナー
  （全件数・不成立件数・敵対的件数・MBO 件数）あり。
- 詳細＝公表日・開始日・終了日・買付価格・プレミアム・TOB 成否・現経営陣の意見・
  目的・買付総額・両者の EDINET コード。**結果テーブル curate の完成形に近い**。
- **公表日と開始日を区別して保持**：事前公表型 TOB では EDINET 届出書（開始日側）
  より公表日が ~2 週間早い。スプレッド形成は公表時点なので
  **C1 の PIT アンカーは公表日 T+1**（EDINET 単独では取れない情報）。
- **欠けるもの→訂正版**：買付予定数の下限・応募株数は無し（EDINET 270 で補完）。
  **バンプ・期間延長の履歴は詳細ページ「コメント」欄に半構造化テキストで存在**
  （「(追記N)M月D日、買付価格を X 円から Y 円へ引き上げ／買付期間を〜まで延長」形式）。
- **最重要 PIT 罠（実例で確定・マンダム 4917 MBO 2025-09 公表）**：
  ヘッダの「買付価格」は**バンプ後の最終価格**（表示 3,105 円、当初は 1,960 円＝
  追記3の「〜円から」で判明。3 回バンプ・8 回延長）。「終了日」も延長後の実日付、
  「買収プレミアム」も最終価格ベースとみられる。
  → **表示価格・終了日・プレミアムをエントリー条件に使うと最大 +58% 級の
  ルックアヘッド**。転記時点で次の 2 群に分離して保存する：
  - エントリー時点既知：公表日／開始日／**当初価格**（最初の価格引き上げ追記の
    「〜円から」。バンプ無し案件は表示価格）／**当初買付期間**（追記1 の
    「〜までとしていた」）／MBO・敵対的フラグ
  - 結果側：最終価格／実終了日／成否／買付総額／バンプ回数／延長回数
- **コメント欄パーサ（`equities/tob_events.py` に同居）**：
  - **走査対象は「目的」欄＋「コメント」欄の両方**（記載場所が案件により異なる。
    マンダム 2025=コメント欄・日付つき／ソレキア 2017=目的欄・日付なし価格列挙）。
  - 正規表現で (日付?, 種別=価格引き上げ|期間延長, 旧値→新値) を抽出。
    日付なし形式は価格列のみ抽出し、変更日は後述の株価段差検出で近似復元。
  - **年の補完**：追記日付は年なし表記が基本・年跨ぎ時のみ年付き
    → 公表日起点の単調増加で推論。
  - **期間延長は独立変数**：延長＝応募不足シグナルかつ年率換算の分母を直撃
    （マンダム：当初 30 営業日 → 実 98 営業日＝年率 1/3 以下）。
    損益は「実終了日まで保有」で定義し、当初予定期間は特徴量側。
  - **テストフィクスチャ＝マンダム（日付つき 8 行）＋ソレキア（日付なし列挙）**。
- **記載慣行の監査結果（スポットチェック済み・2026-06）**：**一貫していない**。
  2017 年より古い案件では訂正記述が見つからず、形式も不統一
  → M&A Online のバンプ履歴は**補助情報に格下げ**（一次ソース不可）。
  「全 18 年への昇格」案は取り下げ。
- **束縛条件の再認識**：C1 の損益計算は **J-Quants 株価履歴（Standard ~10 年）に
  律速**される。2008〜2015 年の案件はバンプ精度以前に株価側が無く検証不能
  → M&A Online の 18 年分は**事前診断（不成立率の長期推移）専用**と割り切る。
- **当初価格・バンプの信頼度 3 層設計（有効窓 ~2016〜2026）**：
  - Tier 1（~2021〜＋フォワード）：EDINET 縦覧期間内。240=当初価格・250=バンプの
    正確な一次ソース。**本則 scope の主戦場**。
  - Tier 2（2016/17〜2020）：EDINET 圏外。M&A Online テキスト（あれば）＋
    株価段差検出で補完。
  - **未記録バンプ検出器（J-Quants）**：友好的成立案件の市場価格は買付価格近傍に
    張り付く性質を利用。「公表後プラトーが表示価格（=最終価格）より有意に低い
    期間が続き、後に段差で切り上がる」案件を未記録バンプとしてフラグ。
    検出器の精度は Tier 1 の EDINET 正解でキャリブレーション（§6.21 mask-first）。
    フラグ案件は除外 or 特徴量化を事前登録で固定。
    放置時の害＝最終価格を当初価格と誤認 → エントリースプレッドの過大評価が
    **バンプ案件（最重要テール）に集中**するため、フラグなしでは使えない。
- **競合 TOB の取り扱い（ソレキア 9867 の教訓）**：同一対象会社に対し
  **入札者ごとに別レコード**が立つ（佐々木ベジ=成立／富士通=不成立）。
  - 案件テーブルに**競合フラグ**（同一 secCode × 期間重複で機械検出）。
    競合案件はスプレッドが買付価格を超える別レジーム＝本則から分離 or 特徴量化を
    事前登録で固定。
  - **年別バナーの不成立件数は競合敗退を含む**＝対象会社レベルでは出口が
    成立している場合がある。Phase A 診断では「案件レベル不成立率」と
    「対象会社レベル不成立率（競合敗退を除く）」を併記
    （不成立リスクプレミアム仮説の見積もりを直接変える）。
- **プレミアム列は使わない**：特別配当案件で符号すら逆転する実例あり
  （日立工機 2017：表示 −19.67%、特別配当考慮で +33.89%）。
  買付価格 × J-Quants 公表日前日終値から**自前で再計算**し、特別配当はフラグ化。
- **利用規約（確認済み）**：事前の書面承諾なきスクレイピング・クローリング等の
  自動化アクセスは禁止。私的使用の範囲に照らし明らかに大量なダウンロードも禁止。
  → **手動転記のみ**。書類本体（届出書・報告書）は M&A Online からではなく
  公式の EDINET から取得（直近 ~5 年）。転記データは `data/`（gitignore）のみ・
  出典と取得日をメタデータ化。

#### 手動転記の段取り（作業最小化）
- **Phase A（数十分）**：19 年分の一覧ページ＝年別バナー＋一覧表を転記。
  → N・不成立率・敵対的/MBO 比率の事前診断（docs/07 C1「先行確認事項」）が完成。
- **Phase B（scope 登録後）**：検証に使う期間（例 2016〜2026・~400 件）に絞って
  詳細ページを転記（買付価格・開始日・意見・目的＋**コメント欄は原文のまま
  1 列に転記**＝バンプ/延長履歴のソース。パースは後段のコードで行い、
  転記時に解釈しない）。全年分を最初から写経しない。
- **PIT 分離**：転記列を「エントリー時点で既知（公表日・価格・MBO/敵対的）」と
  「結果（成否・実終了日・買付総額）」に分けて保存。**現経営陣の意見は要注意**＝
  友好的案件は公表同日に賛同表明が出るが、敵対的案件は数週間後があり得る。
  特徴量に使うなら直近分は EDINET 意見表明報告書（290）の提出日時で時刻付け、
  旧分は結果側の列として扱う。

### 8.3 推奨アーキテクチャ（ハイブリッド）
```
歴史バックフィル（2007〜）: M&A Online（手動 DL・一回限り）
進行形ミラー（毎晩）      : EDINET API（Phase 2 夜間ジョブに追加）
重複期間（直近 ~5 年）    : 両ソース突合 → 不一致レコードは EDINET 優先・ログ化
```
- 19 年遡及で新たに必要になる規律：2007〜2014 年（旧村上ファンド事件後の
  アクティビスト退潮期）と 2015 年〜（ガバナンス改革期）は**レジームが異なる**。
  C2 の事前登録にサブ期間分析（旗艦研究 §6.9 系と同じ）を含めること。
- ※ J-Quants 株価履歴（~10 年）が損益計算の律速。M&A Online の株価圏外の
  古い期間は**診断専用**（§8.2 と同じ割り切り）。

## 9. データ調達マトリクス（確定版・作業範囲の確認用）

| データ | ソース | 取得方法 | 候補 |
|---|---|---|---|
| TOB イベント表（公表日・成否・競合・〜2020 の条件） | M&A Online TOB DB | **手動転記**（Phase A/B のみ） | C1 |
| TOB 書類（240/250/260/270/290） | EDINET API | 自動（~2021〜＋フォワード） | C1 |
| 大量保有（2016〜2021 の穴埋め＋長期診断） | M&A Online 大量保有 DB | **手動 DL** | C2 |
| 大量保有（進行形・縦覧期間内） | EDINET API | 自動ミラー（毎晩） | C2 |
| 有報 XBRL/CSV（BS 明細・10 年） | EDINET API | 自動 | C4 |
| 自社株買い取得枠の発表 | TDnet（**公式 API 無し**） | 今から自前蓄積（後回し） | C3 |
| 株価・財務サマリー・信用・指数・フロー | J-Quants | 既存ミラー（変更なし） | 全部 |

原則と非対象：
- **手動取得は「EDINET で取れないもの」だけ**。M&A Online から貰うのは
  大量保有と TOB の 2 DB のみ。**M&A（合併等）一般 DB は scope 外＝取得不要**
  （C1〜C4 のいずれも使わない）。
- TDnet に公式 API は無い（非公式ラッパーは規約・継続性が未検証につき不採用）。
  C3 は Phase 2 夜間ジョブへの収集追加＝フォワード専用で、当面の取得作業ゼロ。
- 決算短信ベースの財務（業績・予想修正）は J-Quants fins/summary が既にカバー。
  TDnet が真に必要なのは非財務の適時開示（自社株買い取得枠等）のみ。
