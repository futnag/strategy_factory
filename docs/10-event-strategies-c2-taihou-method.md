# 10 — 大量保有 DB（C2）実データ検証と取得方針確定（2026-06）

データ：M&A Online 大量保有報告書 DB（EDINET 2007-04 以降全件）。
検索 UI（対象会社／業種／保有者＝EDINET コード可／提出日範囲）＋検索結果表を
md コピー → パーサで構造化。実サンプル tairyou.md（Evo Fund 25 行）で検証済み。

---

## 1. 実データで確定した仕様

検索結果表の列：報告義務発生日／**提出日**／証券コード／対象会社／業種／種別／
保有割合(%)／増減(%)／保有者（リンクに EDINET コード）／詳細／PDF（書類 ID）。

- **提出日列が存在**＝C2 の PIT アンカーを確保（前回の最大懸念が解消）。
- **保有者リンクに EDINET コード**（`holdingcode_start=E11943`）。検索 UI も
  「保有者＝EDINET コード可」。→ 名簿を **edinetCode ベース**で持てる（表記揺れ回避）。
- **PDF は書類 ID 直リンク**（`/shareholding_reports/S100Y8RE`、`curl .../pdfget2/
  S100Y8RE.pdf` で取得可）。この ID は EDINET docID 体系＝後の EDINET 突合の鍵。
  **MVP では PDF を取得しない**（一覧表だけでシグナルは完成。保有目的・共同保有者が
  要る特徴量拡張段階で初めて取得）。

### 1.1 提出ラグ（特例報告の検出・実測で確証）
- 義務発生→提出のラグは通常 1〜7 日。だが期間検索サンプルで **133 日・148 日**の
  極端な長ラグを確認（横治：1/15 発生→6/12 提出＝148 日）。
  ＝特例報告（機関投資家の集約報告・基準日方式でまとめ提出）が実在。
- **PIT 規律（実証済み・確定）**：エントリーは必ず**提出日アンカー**。報告義務
  発生日でエントリーすると、最悪 148 日先の情報を使うルックアヘッドになる。
  ラグ自体は特例報告か否かの特徴量として保持。

### 1.1b 提出日セルの icon_active.png
- 一部行の提出日・詳細セルに `![](.../icon_active.png)` 画像タグが付く
  （継続中/アクティブ保有のマーカーと推定）。パーサは strip_img で除去するが、
  **付与有無を `active_icon` フラグ列として保持**（特徴量候補。意味は要確認）。

### 1.2 イベント分類（種別列を主・増減を従）
使い方ドキュメントの「増減 0＝新規」は**変更報告書では誤り**（実例：enish 種別=変更・
増減 0.00 だが保有 27%＝新規のはずがない）。正しい分類：
```
増減 = "-"         → admin       (住所/名称変更。ノイズ。除外)
種別 = "新規"      → new_5pct    (初回 5% 超。C2 のエントリーシグナル本体)
種別 = "変更" & 増減>0 → increase (買い増し)
種別 = "変更" & 増減<0 → decrease (売却)
種別 = "変更" & 増減=0 → change_flat (共同保有者異動等)
```

## 2. C2 ユニバース設計（実データが示した必要性）

DB は保有者で検索でき、**あらゆる種類の 5% 超保有者が混在する**。期間検索
（1 ヶ月）の 25 行で保有者は 19 種。性質は大きく 4 タイプに分かれる：

| タイプ | 例（実データ） | C2 本則での扱い |
|---|---|---|
| 真正アクティビスト | 3D インベストメント（西武 HD）／エフィッシモ／村上系／ストラテジック／オアシス／エリオット／DOE5パーセント | **本則ユニバース** |
| エンゲージメント（友好） | みさき／AVI／ダルトン系／バリューアクト | 本則（タグ分離して比較） |
| 事業会社の政策保有 | 光通信／アパ HD／ミダスキャピタル | 除外（経営介入でなく事業保有） |
| オーナー・個人 | 創業者本人（西江・浅井・横治 等） | 除外（インサイダー的だが経営介入でない） |
| トレーディング／純投資 | Evo Fund／マッコーリー等の外資銀 | 除外（流動性業者の在庫変動） |

→【設計含意】C2 シグナル（新規 5%→ドリフト）が「経営介入期待」を捉えるには、
保有者を**スタイルで峻別**し本則をアクティビストに限定する必要がある。
混在 DB から名簿（edinetCode＋スタイルタグ）で抽出するのが前提工程。
スタイルタグは事前登録で固定（後から効いた投資家で絞るのは in-sample 選択＝§6.14 違反）。

> 注：本節の旧版は「サンプルが全行 Evo Fund」という観察に基づいていたが、それは
> 保有者を Evo に指定した検索結果であり DB の偏りではなかった。期間検索の多様な
> 実データで論拠を差し替え（結論=峻別必須 は不変、むしろ強化）。

## 3. 取得方針（確定）

**2 段階・ハイブリッド軸**：
1. **インデックス取得（保有者軸）**：名簿ファンドを EDINET コードで保有者検索 →
   結果一覧を md コピー（`taihou_md/by_filer/{edinet}.md`）。
   目的＝各ファンドが触った対象会社（証券コード集合）の特定。件数少・規約負荷小。
2. **本体取得（対象会社軸）**：①で出た証券コード集合について対象会社検索 →
   その銘柄の大量保有履歴全体を md コピー（`taihou_md/by_company/{seccode}.md`）。
   対象会社軸だと「同一銘柄を巡る複数ファンドの時系列」が 1 ファイルに揃い、
   C2 の保有推移復元・複数アクティビスト同時参入の検出ができる。

- 期間：M&A Online は 2007 年〜全件あるが、C2 損益は J-Quants 株価（~10 年）に律速。
  取得は名簿ファンドの全履歴で可（規約上も件数は多くない）、**検証時に 2016+ で切る**。
- 保存パスに意味を持たせる流儀は TOB と共通（証券コード＝主キー＝J-Quants LocalCode 直結）。
- **PDF は取得しない**（§1）。書類 ID は md 内に温存（EDINET 突合用）。

## 4. パーサ仕様（`parse_maonline_taihou.py`・TOB パーサと別ファイル）

- 入力：`taihou_md/by_company/*.md` と `by_filer/*.md`（同じ表形式なので共通パーサ）。
- 抽出列：oblig_date／submit_date／sec_code／company／industry／kind／holding_pct／
  change_pct／event（§1.2 の 5 分類）／holder_name／holder_edinet／doc_id／submit_lag_days。
- 出力：`taihou_records.csv`（1 行=1 報告書）。
- バリデータ：保有者軸と対象会社軸で取った同一 doc_id の突合（取りこぼし検出）。
  EDINET API ミラー（2021+）との doc_id 突合（M&A Online の精度監査・§6.21 流儀）。
- 検証済み：提出日・EDINET コード・書類 ID・増減 5 分類・ラグ算出すべて動作。

## 6. EDINET DB コネクタの評価（2026-06・実呼び出しで検証）

MCP コネクタ「EDINET DB」を追加・実テスト。大量保有を**構造化済み・API 取得**でき、
手動 md コピーを大幅削減できる。ただし C2 設計を縛る制約が 2 つある。

### 6.1 使えるツール
- `search_shareholders(query)`：filer 名で保有先一覧。各行に issuer_sec_code・
  total_holding_ratio・submit_date。**ステップ1（保有者軸インデックス）を自動化**。
- `get_shareholders(edinet_code)`：issuer ごとの大量保有報告。filer グループ別の
  **最新 1 件**。holder 名・holding_ratio・shares_held・purpose・submit_date・
  doc_id・is_change_report（初回 350 / 変更 360）。**ステップ2（対象会社軸）を自動化**。
- 補助：get_major_shareholders（有報トップ10・FY2014+）、get_shareholder_categories
  （所有者別状況）、get_cross_shareholdings（政策保有明細・C4 の SOTP に有用）。

実証：エフィッシモ（E11852）で 20 保有先、ソフト99（E01057）で 6 filer の構造化
データを即時取得。purpose 欄に「経営陣への助言、重要提案行為等」＝アクティビスト
判定に直結する文言まで入る。

### 6.2 制約1：2021 年 3 月以降のみ（EDINET API v2 limit）
- docs/09 §4 で予測した縦覧期間制約そのもの。**このコネクタは M&A Online の
  代替にならない**。2016〜2021 の歴史は引き続き M&A Online 大量保有 DB（2007〜）
  からの手動取得が必要。
- 含意：C2 は「2021+＝EDINET DB（自動・高精度）」「2016–2021＝M&A Online（手動）」の
  ハイブリッドに再設計。突合は重複期間ではなく境界接続（2021 で連結）。

### 6.3 制約2：filer グループごと「最新 1 件」＝同一 filer の時系列が取れない
- get_shareholders は filer 別最新のみ。**同一 filer の保有割合推移（5%→買い増し）は
  このツール単体では復元不可**。C2 のドリフト起点＝初回 5% 報告（is_change_report=
  false）の提出日が、最新が変更報告書だと取れない懸念。
- 対策：(a) is_change_report フラグで新規/変更は区別可。(b) 初回報告の提出日が必要なら
  EDINET API 直叩き（doc_type 350 の履歴全件）または M&A Online の時系列で補完。
- ただし **C2 の MVP には十分**：search_shareholders の submit_date を「観測時点」、
  is_change_report=false を新規参入シグナルとして使えば、2021+ で PIT ドリフト診断は可能。

### 6.4 再設計した取得手順（手動 → 半自動）
1. **名簿 → search_shareholders**：名簿 filer 名（または EDINET コード）で保有先を
   一括取得。手動の by_filer md コピーを置換。
   ※ 表記揺れ注意：「3Dインベストメント」は 0 件、英名や正式表記が要る場合あり。
   filer_edinet_code が取れたら以後はコードで引く。
2. **保有先 issuer → get_shareholders**：各 issuer の filer 別最新を取得。
   by_company md の代替。doc_id を保持（EDINET 突合・将来の履歴取得の鍵）。
3. **2016–2021 のみ M&A Online**：手動 md コピー（docs/09 §3）で境界より前を補完。
4. **PIT 検証**：submit_date アンカー厳守。初回報告日が要る診断は EDINET API 直で補完。

→ 手動作業は「2016–2021 ぶんの M&A Online」だけに圧縮。2021+ はコネクタで自動化。

### 6.5 申し送り（HANDOFF 追記事項）
- C4（ネットキャッシュ）に get_cross_shareholdings が効く（政策保有株の簿価＝
  含み資産の SOTP 評価）。docs/07 C4 の EDINET XBRL 依存を一部肩代わり可能。
- コネクタはチャット側 MCP。Claude Code 側で同等を使うには EDINET API 直実装
  （docs/08 §1）が必要。コネクタは「設計検証・名簿づくりの偵察」に使い、本番ミラーは
  トラック A の edinet.py に集約する二段構え。

## 7. C2 ユニバース定義の確定（重要提案行為等フィルタ・2026-06）

EDINET DB の「アクティビスト動向」ページ（edinetdb.jp/shareholders?tab=activists）が、
**手編集名簿より優れたユニバース定義**を提供することを確認。これを正式採用する。

### 7.1 定義
- アクティビスト＝**保有目的に「重要提案行為等」を含む大量保有報告書**の提出者
  （ページ冒頭の定義）。法定開示テキストによる客観・網羅・自己更新的な分類。
- §2 で「名簿でスタイル峻別」としたが、その峻別を**保有目的テキストで機械判定**できる。
  手編集名簿の主観（＝どのファンドを入れるか）が排除され、in-sample 選択リスクが下がる。
- コネクタ get_shareholders の **purpose フィールド**に「重要提案行為等」が含まれるかで
  Claude Code 側でも同一フィルタを再現可能（実例：エフィッシモのソフト99 保有目的＝
  「投資及び状況に応じて経営陣への助言、重要提案行為等を行うこと」）。

### 7.2 手編集名簿の役割を格下げ
- registry は「ユニバースを決めるもの」から「**グループ名寄せ・スタイルタグの補助**」に。
  1 ファンド複数 EDINET コード（村上系 city11/cityfirst/reno、ダルトン LLC/Inc）の
  dedup と engagement_hard/soft タグ付けにのみ使う。ユニバースの母集合は purpose フィルタ。
- activist_registry_draft.csv を 34 グループに拡張（叩き台 9→34）。アクティビスト
  ページから抽出。EDINET コード判明 11／要特定 23（API の filer 検索や purpose 逆引きで補完）。

### 7.3 ページが示す追加の知見
- **推定取得単価**列あり（報告書記載の取得資金合計÷保有株数）。C2 の含み損益・
  エントリー水準の参考になるが、概算値かつ最新ポジションベースなので検証では
  自前計算（J-Quants 株価）を優先し、これは突合用。
- 200 ポジションは**最新・現在保有中**に限られる疑い（売却済み＝ドリフト完了形が
  欠落）。コネクタ get_shareholders の filer 別最新制約と同根。過去の参入→売却の
  フルサイクルが要るなら、§1 の手動 CSV（全件スナップ）か EDINET API 直で補完。
- 新興アクティビスト（DOE5パーセント・fundnote・Be Brave 等、社名で意図表明）も
  purpose フィルタなら自動で入る＝手編集では取りこぼす層を捕捉。

### 7.4 実装への指示（HANDOFF 反映）
- C2 ユニバース構築＝「get_shareholders（or EDINET API）で purpose に重要提案行為等を
  含む報告を全 issuer から抽出」を第一段に。registry は名寄せ・タグ付けの後処理。
- これにより「名簿 8 グループを回す」アプローチは「purpose フィルタで母集団を取り、
  registry でグループ化」に置き換わる。ユニバースは概算 ~150 から大幅に増える見込み
  （200 ポジション/最新時点だけでも 30+ グループ）。フォワード前提は維持しつつ、
  サンプル増で記述統計の信頼性が上がる。

## 8. STEP2 実装（EDINET ネイティブ・トラックA）— 2026-06

§6 の MCP コネクタ（チャット側偵察用）と並行し、本番ミラーを EDINET API 直で実装した
（§6.5 の二段構え）。コネクタの「最新1件・2021+」制約を受けず、初回 5% 報告の提出日
（PIT アンカー）を含む全件をローカル parquet に固定できる。

### 8.1 実装物
- `invest_system/equities/large_holdings.py`：府令060 本体（type=5 CSV・`jplvh_cor`）から
  保有目的・保有割合・提出者・本体タイトルを抽出。`report_class()`（タイトル判定）、
  `is_special_report()`（formCode 接頭辞）、`fields_lvh()`、`tag_filer()`（registry 名寄せ）、
  `enrich_holding()`（1 報告→特徴量＋タグ）。要素 ID は docs/08 §7.1 point5。
- `examples/edinet_lvh_backfill.py`：formCode 010000（一般・新規候補・≈4,884 件）を
  スキャンし `data/edinet/large_holdings.parquet` に保存。冪等・再開可（body_ok スキップ）。
  C2 エントリー母集団＝`report_class=='new' & is_important_proposal`。
- `tests/test_large_holdings.py`（6 件パス）。

### 8.1b スキャン完走結果（2026-06・4,872 件 body_ok）
- report_class 内訳：new 4,492 / change 338 / unknown 37 / correction 5（010000 は ~92% が
  新規＝スキャン対象として妥当）。
- **新規×重要提案（生の母集団）545 件**。保有割合バンド：<5% 109・5–10% 213・10–20% 19・
  20–30% 18・**30–50% 51・≥50% 135**（高保有 186 件は買収 SPV 偽陽性＝§8.3）。
- **コア母集団（保有割合<30%）359 件 / ユニーク提出者 ~110 / canonical_group 23**。
  年別：2022=51 / 2023=50 / 2024=84 / 2025=110 / 2026=64（partial）。想定（30+ グループ）を
  上回る規模で purpose フィルタは網羅的に機能。トップは村上系(49)・AVI・Zenner・GMO・
  ストラテジック・エリオット・エフィッシモ等の真正アクティビスト。

### 8.2 確定知見（docs/08 §7.1 の formCode 記載を訂正）
- **新規/変更/訂正は本体タイトルでのみ判別可**（formCode・docTypeCode 不可）。旧 HANDOFF/
  docs の「01xx=新規」は誤り（`010002` は 100% 変更報告書）。詳細 docs/08 §7.1 point1/4。
- **特例報告（formCode 02/03）はアクティビスト母集団から除外してよい**：法定上 重要提案
  行為等の意図がない機関投資家専用。実測でも 030000 の重要提案ヒット 0/25。→ スキャンは
  一般新規 010000 に限定（新規イベントは事実上すべてここに入る）。

### 8.3 purpose フィルタの偽陽性（C2 シグナル仕様への申し送り）
- 保有目的フィルタ単独は **TOB 後スクイーズアウト目的の買収 SPV** も拾う（実例：
  MBK Wellness Holdings 92.8%、PTCJ-2 ホールディングス 81.35%＝高保有割合＋重要提案 purpose
  だがアクティビズムではない）。C2 シグナルでは **保有割合バンド（例 5–30%）で除外**するか、
  TOB 案件テーブル（tob_deals）と突合して買収者を落とす。これはユニバース抽出でなく
  シグナル定義側の論点（事前登録で固定）。
- registry はユニバースを縛らない（§7.2）が、purpose フィルタが拾った名簿外の真正
  アクティビスト（実例：タイヨウ・パシフィック・パートナーズ E37410＝著名エンゲージメント
  だが名簿未登録）はタグ付けの取りこぼし。registry へ随時追記してよい（タグのみ・
  母集団は不変＝in-sample 選択にならない）。
- **名寄せ補修（2026-06 実施）**：スキャン結果の filer_edinet を使い、既存グループの欠損
  EDINET コードを補充（valueact/NAVF/kaname/be_brave/axium/old_peak/miri/ugs/mi2）＋
  taiyo を新規追記。コア母集団の名簿一致が **160→249 件（45%→69%）** に向上。残り 110 件は
  小規模・新興ファンドや非アクティビスト（機関投資家・個人）で、母集団には残るが未タグ。
