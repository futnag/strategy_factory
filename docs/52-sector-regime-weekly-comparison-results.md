## 1. 検証の意図

旗艦戦略（value + ロングティルト PEAD）の上に載せる **セクター単位のリスク環境モニタリング** のため、次を明らかにする。

1. **S33 セクター週足**で、複数のレジーム検知手法のうちどれが統計的に妥当か
2. レジームを **高ボラ / 低ボラ** として解釈したとき、**翌週リターン・ボラの予測**や **状態の持続性** に差があるか
3. セクター特性（ディフェンシブ / サイクリカル / ニュートラル）ごとに **最適手法が異なるか**
4. 本番運用に向け、**週次ウォークフォワード・先読みなし** で再現可能か

本検証は **戦略の judge_grid 裁定ではない**（診断・手法選定パイプライン）。目的は「どの検知器を週次ゲートに使うか」の材料化。

関連: `docs/27-regime-analysis.md`（指数・市場全体の事後分析）、`docs/31-value-pead-premium-by-regime.md`（旗艦×レジーム）。

## 2. 検証方法

### 2.1 データ

| 項目 | 内容 |
|------|------|
| ソース | `--source project` → `data/features/returns.parquet` を S33 中央値集約 |
| 頻度 | 週足（`W-FRI`・金曜締め） |
| セクター | 流動性・期間条件を満たす **34 セクター**（最低 260 週 ≈ 5 年） |
| 特徴量 | `log_return_w`・`realized_vol_w`・`mom_20w`・`rel_strength_w` |

### 2.2 比較手法（12 本）

| 系統 | 手法 |
|------|------|
| HMM | `hmm_2` / `hmm_3` / `hmm_4` |
| 変化点（CPD） | `cpd_pelt` / `cpd_binseg` / `cpd_bottomup` |
| GMM | `gmm_2` / `gmm_3` / `gmm_4` |
| Markov Switching | `markov_2`（refit_every=16）/ `markov_3`（同） |
| オンライン変化点 | `bocpd` |

### 2.3 推定ルール（先読み禁止）

- 各週 `t` で **≤t のデータのみ** を用いるウォークフォワード
- ウォームアップ **104 週**、再学習間隔 **4 週**（Markov は **16 週**）、ローリング窓 **156 週**
- 標準化・変化点・フィルタはすべて当該窓内のみ
- 評価の `shift(-1)` は **翌週予測力の検定用**（推定には不使用）

### 2.4 複合スコア（セクター内ランキング）

| 軸 | 重み | 内容 |
|----|------|------|
| 予測力 | 0.40 | 翌週ボラ・リターンとの相関、R²、方向 Hit 率 |
| レジーム質 | 0.25 | 状態間分離、平均持続週数、切替頻度 |
| 安定性 | 0.20 | HMM のみブートストラップ一致率（他は 0.5 固定） |
| 経済的意味 | 0.15 | レジーム間リターン・ボラの t 検定 |

### 2.5 実行

```bash
python examples/sector_regime_comparison.py --source project --output output/sector_regime --jobs 1
```

- **2026-06-29 フルラン**: 34 × 12 = **408 手法・全成功**、所要 **16,316 秒（約 4.5 時間）**
- ログ・進捗・失敗 WARNING はセッション中に `pipeline.py` / CLI を改善済み

## 3. この方法を採用した意図

| 設計判断 | 理由 |
|----------|------|
| **週足** | 日次ノイズを抑え、個人運用の週次リバランス・ナイトリー更新と整合 |
| **セクター単位** | 旗艦は銘柄横断だが、リスクは業種集中。S33 は既存データで PIT 構築可能 |
| **12 手法の横並び比較** | 単一手法（GMM のみ等）に固定せず、セクターごとの最適検知器を探索 |
| **ウォークフォワード** | レジーム推定の先読みを排除（`docs/27` の事後分析との差別化） |
| **複合スコア** | 予測だけでなく「状態が経済的に意味あるか・持続するか」を同時に見る |
| **高ボラ軸の統一解釈** | `_high_vol_state_index` で `regime` / `regime_prob` をボラ環境として横比較可能に |

採用しなかったもの: 日次リアルタイム検知、銘柄単位レジーム、転換即時の機械売買ルール（別フェーズ）。

### 4.5 解釈（レジームの意味）

- **レジーム** ≈ 多変量特徴（ボラ中心）で切った **市場環境の区分**（厳密にはボラのみではない）
- 出力は **`regime`（離散ラベル）+ `regime_prob`（0〜1）**；生の `realized_vol_w` は並行監視用
- **転換検知の時間分解能は週次**（金曜確定後）。転換から 1 週以内の「早期」検知は設計上期待しない

### 4.6 投資への含意（本検証の範囲）

| 向く用途 | 向かない用途 |
|----------|-------------|
| 週次リスクモニタリング | 転換のたびの高頻度売買 |
| value+PEAD の **露出ゲート**（高ボラで新規停止・縮小） | 翌週方向の単独 α（Hit ≈ 50%） |
| セクター配分上限の調整 | 全セクター一律 GMM 固定 |

## 6. 限界と次ステップ

### 限界

1. **ベスト手法選定は in-sample**（全期間スコア最大）→ 本番採用前に OOS / 直近サブ期間の確認が必要
2. **安定性スコア**は HMM 以外 0.5 固定のため、非 HMM 間の安定性比較は未差別化
3. **上流データ**（`returns.parquet`）の PIT 品質は本スクリプトでは未監査
4. **judge_grid 未接続** — ゲートとして旗艦に効くかは未裁定

### 推奨次ステップ

1. `best_per_sector.csv` を週次更新ルックアップとして運用化（`sector → method`）
2. 高ボラ `regime_prob` 閾値での **value+PEAD ゲート**を事前登録し一回判定
3. ベスト手法の **2023+ サブ期間**でスコア安定性を確認
4. `docs/03` に本レポート（§52）への参照を追記（consolidate 時）
